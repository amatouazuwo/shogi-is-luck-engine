# 「将棋は運ゲー」CPU難易度・アマ棋力換算の校正手順

## 現段階の認定範囲

ゲーム側の5段階は「ふつう（既存簡易CPU）」「アマ5級を目標（100ms）」「アマ初段を目標（500ms）」「アマ四段を目標（1500ms）」「全力（上限6000ms）」である。これらは**探索時間を分類する仮の設定**であり、段級位の実力を認定したものではない。設定値の単位は探索時間（ミリ秒）であり、棋力の単位ではない。全力はアマ段級位の確定値を持たない。

**棋力認定への道筋は、(1)内部の相対順位確認 と (2)外部のアマ段級位基準との照合 を分けること。**

### 1. 同一エンジンの相対差（実装済み）

- 旧500ms対1500msは[CI 45051961118](https://github.com/amatouazuwo/shogi-is-luck-engine/actions/runs/45051961118)で12局、1500ms側7勝、500ms側0勝、未決着5。**小標本かつ未決着があり、アマ段級位を推定できない。**
- 新100ms対500msは[CI 45095505711](https://github.com/amatouazuwo/shogi-is-luck-engine/actions/runs/45095505711)の結果を確認すること。開始局面の先後入替、落とし穴と3×3ブラックホール、上限120手を使用。未決着は中立のまま。
- `benchmarks/strength/ci/difficulty-scorecard.mjs` はWASM/Worker SHAの一致、ペアの対称性、結果数、勝者と打ち切り理由の整合をチェックする。証拠はGitHub ActionsのJSONLログに残す。勝率下限=確定勝ち数/総局数、上限=(確定勝ち数+未決着数)/総局数。強さの確定はしない。
- 今後1500ms対6000msも同一手順で比較する。ただし最大設定の実ゲームの残時計上限は`残り時間/12`、旧match harnessの残時計上限は`/20`なので、実装と厳密に揃える変更が必要。コードだけで勝敗が同じになるとは限らない。CPU着手前ディレイ等、実ゲームとの差も別に記録する。
- 検証対象は複数の未使用初期陣形・穴/ブラックホール配置。開始局面の相関を「別々の独立した標本」として集計しない。

### 2. アマ段級位の外部基準との照合（未着手・今後必要）

- アマ段級位には単一の普遍的な数値基準がないため、どの大会、道場、将棋サービスの等級を使うかを定義し、**同じ基準で級位者・有段者を参照**する。サービス間の段位は無条件に換算しない。
- 対局相手には事前に検証目的を説明し同意を得る。**実名、アカウントID、IP、棋譜以外の個人情報は収集せず**、統計上必要な棋力帯・先後・持ち時間・勝敗・CPU設定ID・ゲーム/Worker/WASMバージョン・盤面シード・レアイベント・端末種別を記録する。ゲーム本体が同意なく自動送信する設計にはしない。
- 各目標で基準棋力のある複数相手と先後を均等化し、初期陣形や障害物配置、対局時間（3分切れ負け）も揃えて複数セット実施する。**通常盤面と1%イベントありの本ゲームを分けて報告**する。CPU同士の結果だけで級段位を認定しない。
- 勝敗は時計切れ・詰み・合法手なし・中断・データ破損・検証用手数打ち切りに分類。手数打ち切りを引き分けや負けに変換しない。
- 目標実力から乖離した場合は`shogi-is-luck/scripts/cpu-difficulty.js` の設定を調整する。**探索時間を短くするだけでアマ5級相当の弱さが得られない場合**は、合法手のみからの候補選択制限や評価の弱め方を専用の検証ブランチで比較し、ゲームの合法性・ルール・時計を優先する。故意の反則手やランダムな時間切れを弱さの手段として採用しない。
- 誤差と未決着が十分に小さくなり、基準棋力帯との関係が確認できるまで、ゲームUIは「アマ◯級／段を目標」の表示とする。

### 3. リリース前ゲート

棋力ラベルを確定表示へ変更する前に、相対棋力の順序・外部基準との対局・端末性能差・特殊イベントからの復帰・時計管理・合法手検証をすべて確認する。実験結果を理由に自動マージ・本番デプロイしない。

安全：現在の検証コードはDraftの `chatgpt/strength-ci` とゲーム側 `chatgpt/continuous-rsshogi-develop-sandbox` のみ。Render・`main`・`develop` 未変更。
