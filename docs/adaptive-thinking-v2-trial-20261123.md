## v2の設計仮説

すべての「取る手が2つ以上ある局面」を特別視せず、王手や明確に選択肢の多い交換局面に限定して考える。

| 判定条件（独立C++審判の特徴） | 探索の上限 |
|---|---:|
| 王手を受けており合法手3以下 | 6秒 |
| 王手を受けており合法手4以上 | 3秒 |
| 王手ではないが合法手5以下 | 3秒 |
| 王手ではなく、駒取り候補5以上かつ成り候補2以上 | 2秒 |
| それ以外 | **1秒** |

低時計の安全制限：残り60秒以下→1.5秒以内、30秒以下→750ms以内、10秒以下→250ms以内。さらにゲームの残時計÷12と150ms安全余裕を全て維持する。**最大6秒上限は不変**。

前回の実対局222手の特徴ログにこの条件を**机上で適用した場合**、1秒候補155手（約69.8%）、2秒39手、3秒17手、6秒11手になる。ただしこれは**過去のログへの再分類**にすぎず、実際にv2で指すと局面遷移が変わるため、実戦の回数や棋力は予測できない。過去ログから条件を作ったことによる過学習を避けるため、新しい評価盤面のシードは**20261208**に変更し、以前の20261206を再利用しない。

## 実装

- `benchmarks/strength/ci/adaptive-think-policy-v2.mjs`：v2の純粋関数。パラメータ検証、通常局面1秒、王手への長考、低時計で短縮
- `benchmarks/strength/ci/adaptive-think-policy-v2.test.mjs`：一般の駒取りだけでは長考しない、王手への特別配分、時計の安全制限を単体試験
- `benchmarks/strength/ci/match.mjs`：両側に別々の可変思考方式を設定可能。候補v2と対照v1を直接同時に走らせる。双方に独立C++審判の特徴取得コストを正しく計上
- `benchmarks/strength/ci/difficulty-scorecard.mjs`：候補・対照の各手についてv1/v2の選択結果・特徴抽出時間・合法手・探索予算・時計消費を別途計算し、食い違えばCI失敗
- `benchmarks/strength/ci/adaptive-v2-scorecard.mjs` と単体試験：両側の勝敗、未決着、残時計、実探索時間、探索深さ、通常1秒選択比率を分けて集計
- `.github/workflows/adaptive-v2-head-to-head.yml`：新しいシード20261208の落とし穴＋ブラックホールと先後入替で、v2 vs v1、v2 vs 固定1秒を実対局比較。最大300手、上限・千日手未裁定は中立未決着

## 合否と注意

**改善案はv2が実際に勝ち越すかどうかだけでなく、持ち時間をどれほど節約し、長考しすぎず、合法手・時計を守れるかで評価する。** 先後交換4局だけでは最適な難易度や強いCPUの確定は不可能。王手・駒取り候補数だけでは静かな必至や詰み筋を拾えないため、今後の改善余地がある。

本番ゲームの難易度はアマ5級・アマ初段・アマ四段の**未校正目標**と簡易CPU・全力CPUの5段階を維持。今回の方式は検証用ブランチだけ。ゲーム`main`・`develop`・Renderにはマージ・デプロイしない。
